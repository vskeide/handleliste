Read-only Supabase checks found no duplicate list/meal lines and no item route

Validation: 13 regression tests pass (`npm test`), `npx tsc --noEmit` passes, and the

## Open findings, in priority order

### 1. P1 — Upgrade the unsupported framework before adding features

`package.json` and the installed lockfile use Next.js **14.2.35**. `npm audit` reports
24 affected package entries across the whole dependency tree: 1 critical, 13 high,
8 moderate and 2 low. With development dependencies omitted it reports 10 entries:
1 critical, 6 high, 1 moderate and 2 low. These are package entries, not 24 proven
exploits against this deployment; transitive tools and unused features affect counts.

The relevant exposure is real: this app uses App Router and Server Actions, which
are affected by server-side denial-of-service advisories. Do not imply that every
image/cache/Windows advisory applies to the Linux Vercel deployment. The current
code does not use `next/image`, `use cache`, or a custom server.

Vercel's [May release](https://vercel.com/changelog/next-js-may-2026-security-release)
lists all Next.js 14 versions as affected, with fixes on supported newer branches.
The [October 14 release](https://nextjs.org/blog/nextjs-security-update-october-14-2026)
also fixes a Server Actions DoS and publishes 15.5.28 / 16.4.1. The registry currently
offers newer patches, so resolve the latest patched version when upgrading.

**Smallest sensible action:** migrate to a currently patched supported Next.js branch,
align `eslint-config-next`, review the async cookies/route APIs, and verify login,
add/tick, meals, map saves and PWA behaviour. Refresh compatible transitive packages
in that work. Avoid `npm audit fix --force` as an unreviewed major upgrade. `zod` is
currently unused and can simply be removed; the old SSR wrapper should be reviewed
with the browser Realtime client rather than upgraded blindly.

### 2. P1 — Offline writes are not yet dependable

Files: `lib/hooks/use-outbox.ts`, `lib/hooks/use-realtime-list.ts`, list client
`runOp`, `send`, `opAnswered`, and queue-restoration effect.

- Direct writes run concurrently while `waiting` is zero. Add a new item and immediately
  change its quantity/tick it: the follow-up may reach the server before creation.
- Refetches preserve pending **adds** only. A queued quantity, tick or removal can be
  replaced by an older server row on the next poll/broadcast/focus refresh.
- The queue retries creates with client IDs, but `createItemAndAddToList` treats an
  already-created item as a conflict. If the first response was lost after commit,
  retry can remove the optimistic line and report failure despite persisted data.
- When a duplicate add returns a different existing line ID, queued operations still
  reference the temporary ID. They are not remapped.
- `opAnswered` handles refused adds/creates, but ignores server refusals for quantity,
  toggle and remove. Outbox then discards those operations.
- Restored operations only contain IDs for existing products. If an offline add's
  product was not in the cached server-page catalogue, its row may be invisible after
  reload. Bulk additions and meals bypass the queue entirely and clear typed input
  before the request succeeds.

**KISS fix:** keep localStorage, but use one serial write queue for both online and
offline changes; make create/add retries idempotent; remap confirmed IDs; overlay
pending operations on each refreshed list; surface rejected operations. Test response
loss after commit, add→change→tick, reload offline and reconnect on two phones. A
new sync service or full IndexedDB framework is not required for this household.

### 3. P1 — Duplicate prevention and quantity merging need database guarantees

Files: `lib/actions/lists.ts:addItemToList`, `lib/list-merge.ts`; live indexes on
`list_items`, `meal_items`, `template_items`.

Check-then-insert permits two phones to add the same product concurrently. There
is no unique `(list_id, item_id)` constraint. The same pattern exists for meals and
templates. `mergeIntoList` also reads a quantity, adds in JS, then writes an absolute
value: two simultaneous increments can overwrite each other. Reporting write errors
is fixed above; atomicity is not.

**Action:** recheck duplicate groups immediately before migration, then add composite
uniqueness for each parent/item pair. Add one narrowly scoped transactional database
function for merge/add, with explicit ownership and service-role-only execution.
No existing rows need cleanup today; do not invent a destructive deduplication rule.

### 4. P2 — Logout does not remove cached household pages

Files: `public/sw.js`, `lib/actions/auth.ts:logout`, settings logout handler.

Pages and `/__last-list` are cached without a household namespace. Logout clears only
the cookie. On a shared phone, an offline navigation can still display a previous
household's cached list; localStorage queues also survive account changes.

**Action:** scope cached pages and queues to the household and clear that household's
cached/private data on logout. Explicitly handle unsent changes before clearing them.
Do not remove offline access: it is useful in shops.

### 5. P2 — Multi-step saves can lose data or leave half-finished objects

`saveWalkOrder` deletes the old layout before inserting the replacement, ignores DB
errors and is followed by an unconditional “saved” UI. A failed insert can erase the
existing order. Save-template, create-from-template, save-starter-meal and recipe
import can likewise leave a parent with no/some children. Several delete flows first
delete children, then delete the parent even though the FK already cascades.

**Action:** use one transaction for each parent/children operation, and use existing
cascading parent deletes. Return failures through the UI. Add a regression case that
fails the second write and verifies the original state survives. Map upsert errors
are fixed in this pass; walk-order replacement still needs a transaction.

### 6. P2 — Route learning delays ticks and is not retry-safe

`toggleListItem` updates purchase statistics and routes before saving the checkbox.
Ticking one item triggers ownership lookups, four reads, counter update, route reads
and writes, and finally the checkbox write. Repeated `checked=true` calls count a
purchase again; parallel requests can lose counter updates or calculate the same
trip position. Route learning also runs when location is idle/denied, because only
the explicit `away` state disables it. GPS checked only on open/focus can be stale.

**Action:** atomically change the checkbox only if its previous state differs; learn
once per actual transition. Update counters/routes in that transaction or an explicitly
best-effort step after the important write. Keep manual shop selection as the fallback.
Do not build background location tracking.

### 7. P2 — Repeated new products can reject a whole multi-add

`handleMultiAdd` and `handleAddStarter` match against a fixed copy of known items.
If the same new catalogue product appears twice, they generate two IDs with one name;
the household/name unique index rejects the batch. A product created on the other
phone after page load can cause the same failure. This pass makes the failure visible,
but does not yet resolve it.

**Action:** reuse one canonical item per normalized name within a batch, resolve
existing household IDs on the server, and retain entered text until success. One
shared get-or-create helper is sufficient.

### 8. P2 — Some quantities do not behave as typed

In list `handleAddItem`, adding `3 egg` when eggs are already present increments by
one; measured quantities open a picker, and re-adding a checked item restores its old
quantity. The typed amount is retained only for a new line. Also,
`scaleQty('0.25 kg', 0.5)` returns `0.5 kg`: the half-kilogram minimum can increase
amounts when reducing portions. Equivalent gram quantities behave differently.

**Action:** distinguish an explicit typed amount from the default one, merge that
amount for existing lines, and scale weight/volume in base units before rounding.
The decimal-comma split/parser inconsistency is fixed in this audit.

### 9. P2 — Settings and several screens have unreliable error states

Rapid adults/children taps send overlapping absolute writes (`saveSize`) that can
arrive out of order. Rejected saves are displayed beside the optimistic new numbers,
with no rollback; network exceptions are unhandled. Other examples are meal deletion,
list creation, template edits and “same as last time”: missing catch/finally handling
can leave spinners stuck, hide rows that were not deleted, or discard user input.

**Action:** serialize/disable only the affected save while pending, keep the previous
value, and show a short retry message. Add a small route error boundary with a Retry
button. Avoid introducing a global state/error-management library for this.

### 10. P2 — Session lifetime and PIN throttling need tightening

`lib/session.ts` signs only the household ID. The cookie expires after 30 days in the
browser, but the signature has no server-enforced expiry or revocation version. A
copied cookie stays valid until key rotation. PIN failures are incremented with a
read/modify/write in `joinHousehold`, so parallel attempts can overwrite each other's
counts. Public household creation also has no request throttle.

**Action:** add a signed expiry/version and atomic attempt counting. Keep the household
PIN model for now; personal email logins are not needed to address these bugs. Do not
invalidate both phones' sessions without a planned rollout.

### 11. P3 — Useful cleanup and performance follow-ups

- Root “latest list” selection does not filter `is_active`, while the overview does.
  Define active-list behaviour consistently before adding archive UI.
- Service worker uses a fixed `v1`, stores unversioned icons with cache-first, does not
  use `event.waitUntil` for asynchronous page-cache writes, and only caches full
  navigations. Next client-side route navigation is not guaranteed to refresh that
  cached page. Bound retained page versions and test a deployed upgrade/offline reopen.
- The middleware constructs a Supabase Auth client but does not authenticate anything;
  actual authentication is the household cookie. Remove that unused path and unused
  `createServerSupabaseClient`, `useSession`, old `searchLocal`, imports and `zod` when
  upgrading dependencies. Do not remove the action/page ownership guards.
- The list client is approximately 1,300 lines with repeated row markup and some broad
  `any` types. Extract a shared list row and add/search area when next changing them;
  a wholesale rewrite provides little immediate benefit.
- Icon-only list controls need accessible names and larger finger targets. Browser zoom
  is enabled again in this pass. Keyboard focus/dialog handling should be checked on
  the real phones rather than redesigning the UI.
- `keepalive` permits requests when `CRON_SECRET` is absent. Fail closed in production
  and avoid returning raw DB errors. This endpoint exposes no list contents, but the
  fallback is unnecessary for a production cron.
- Recipe import is a line/quantity parser, not an arbitrary-recipe parser. Full pasted
  instructions/headings can become products. Keep its promise narrow until there is
  an ingredient preview/selection step.

## Database tuning: keep it proportional

Supabase performance advisors flag 21 uncovered foreign keys, one unused index, and
duplicate household-code indexes (`households_household_code_key`, `idx_households_code`).
These are not evidence of noticeable slowness at this household's scale. Prioritize
the uniqueness constraints above. If needed next, index `meal_items(meal_id)`,
`template_items(template_id)`, `meals(household_id)` and `list_templates(household_id)`
after inspecting query plans. Keep the constraint-backed household-code index and
remove its redundant standalone twin in a reviewed migration. Do not add 21 indexes
or remove indexes solely because a fresh statistics counter says “unused”.

Advisor explanations: [foreign keys](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys),
[duplicate indexes](https://supabase.com/docs/guides/database/database-linter?lint=0009_duplicate_index).

## Feature shortlist

Only add these after the P1 work; each can fit into the current screen.

1. **Undo an accidental removal.** A short-lived “Angre” control after deleting one
   line. Existing fullscreen picking already has undo; ordinary line removal does not.
2. **Collapse picked items.** “Plukka (12)” expands on demand so long trips stay tidy.
   No extra mode or settings page.
3. **One plain note per list.** For “ta med posar” or a useful brand/size reminder.
   No rich text, attachments or tagging system.

Already present: local search, frequent items, same-as-last-time, templates, meal scaling,
manual shops, GPS suggestion and fullscreen picking. Improve those before adding
overlapping features. Defer price comparison, product scanning, stock tracking,
weekly planning dashboards, background geofencing, gamification and complicated AI
parsing. The planned assistant connector can stay small: revocable token plus a few
list/meal actions, after writes are safe to retry.
